### G1

**Historical-cutoff runs leak the live Yahoo price and 52-week range into the valuation**  
Severity high · confirmed · effort S

Locations: `src/lib/research/handlers/asset-valuation.ts:186-210`, `src/lib/research/handlers/asset-valuation.ts:213-222`, `src/lib/research/handlers/asset-valuation.ts:346`, `src/lib/research/handlers/asset-valuation.ts:374`, `src/lib/research/handlers/asset-valuation.ts:430`, `src/lib/research/handlers/asset-valuation.ts:513-519`, `src/lib/research/sources/corpus.ts:365-367`, `src/lib/research/sources/corpus.ts:441`, `src/lib/research/sources/corpus.ts:464`, `src/lib/market-data/price-history.ts:110`, `src/lib/market-data/price-history.ts:264-310`, `src/lib/market-data/service.ts:168-185`

- **Evidence:** The market snapshot is always a live fetch with range=5d (corpus.ts:365-367). corpus.ts deliberately drops regularMarketPrice and the 52-week fields whenever a market-data cutoff is set (corpus.ts:441, :464). asset-valuation.ts:186-210 reads the same snapshot chunk with no cutoff check: it copies meta.regularMarketPrice, fiftyTwoWeekHigh and fiftyTwoWeekLow, sends them to the model as current_market_snapshot in both the bank path (:374) and the operating path (:430), and falls back to the live price when valuationDatePrice() returns null (:346). It then labels that price source yahoo_chart_snapshot (:513-519). valuationDatePrice returns null when no stored close exists within 7 days before the cutoff (price-history.ts:110). Two things make that likely: syncAssetPriceHistory never throws and only records its error (price-history.ts:264-310), and syncDailyHistory takes min/max over all stored bars, not the run's window, so a gap inside the window is never fetched (service.ts:168-185). The DB holds 6 MSFT runs with market_data_cutoff_at 2022-01-01 or 2023-12-30.
- **Failure scenario:** An MSFT run with market_data_cutoff_at 2022-01-01 executes in October 2026. The valuation-analyst prompt shows the October 2026 price and 52-week range as the 'current' market. Separately, if the Yahoo history fetch fails, or stored bars cover 2016-2019 and 2020-2026 but not December 2021 (left by earlier runs with other cutoffs), the upside, reverse valuation and current_market_price are all computed from the 2026 price. The run completes with no warning.
- **Fix:** In asset-valuation.ts, treat the run as historical when the snapshot's retrieved_at is more than 1 day after the cutoff. For historical runs, drop regular_market_price and the 52-week fields from marketSnapshot (mirror corpus.ts:441/464), and never fall back to the snapshot price: withhold with 'no stored close on or before the cutoff'. In service.syncDailyHistory, compute first/last inside [start, end] and check for gaps over 7 days with a lag() query; refetch the whole window when either fails (persistPriceBars already ignores conflicts).
- **Verifier:** asset-valuation.ts:186-210 copies meta.regularMarketPrice and the 52-week fields from the live range=5d snapshot (corpus.ts:365-367) with no cutoff check, and sends them as current_market_snapshot (:374, :430). corpus.ts:441/464 drops those same fields when a cutoff is set, so the two paths disagree. :346 falls back to the snapshot price when valuationDatePrice returns null (price-history.ts:399-402 applies a 7-day gap limit), and :513-519 labels that price yahoo_chart_snapshot. service.ts:168-185 checks only min/max over all stored bars, so a gap inside the window is never refetched.

### G2

**A zero written as a word ('no', 'none') in a primary statement makes historical_record fail every time, after 3 wasted repair calls**  
Severity high · confirmed · effort S

Locations: `src/lib/research/history/filing-statements.ts:80-84`, `src/lib/research/history/filing-statements.ts:130-131`, `src/lib/research/handlers/historical-record.ts:172-174`, `src/lib/research/repair/statement-repair.ts:64-118`, `src/lib/research/repair/statement-repair.ts:50`, `src/lib/research/repair/statement-repair.ts:79`

- **Evidence:** The fact parser supports only num-dot-decimal, numdotdecimal, zerodash, fixed-zero, numdash and fixed-zero. A dash is the only text it maps to 0; anything else goes through Number(text), so a fixed-zero fact reading 'no' or 'none' becomes null and adds an 'Unresolved fact' warning. ixt-sec:numwordsen is unsupported outright (filing-statements.ts:80-84). filingCoverage marks a filing 'incomplete' when any non-segment statement table has a warning (:130-131), and historical-record.ts:173 then throws. The repair specialist runs up to 3 model calls (statement-repair.ts:64-118), but it can only relabel tables and is forbidden from overriding heading-identified tables (:50, :79), so it can never clear a warning. Verified with the real parser: I ran extractFilingStatements on all 166 stored 10-Q/10-K files. The stored NuScale Power FY2021 10-K (source_document e8e16db7) yields balance-sheet warnings 'Unresolved fact us-gaap:CommonStockSharesIssued' from ixt-sec:numwordsen facts. Across the corpus, fixed-zero wraps 'no' 357 times, 'No' 79 times and 'none' 12 times, and ixt-sec:numwordsen appears 1,225 times. Most of these sit in notes, but any one inside a primary statement is enough to trigger the failure.
- **Failure scenario:** A deep dive on NuScale with a cutoff that keeps the FY2021 10-K in the 20-quarter window, or on any filer that tags 'none issued' on the face of its balance sheet, reaches historical_record. The parser warns, 3 paid repair calls fail, and the stage throws. Under RM2 the whole run ends, and every retry fails the same way because the input is deterministic.
- **Fix:** In the fact parser (filing-statements.ts:80-83), set raw=0 for the fixed-zero and zerodash formats whatever the text says. Add numwordsen with a small word map (no/none/nil/zero=0, one..twelve). Optionally count only warnings on non-dimensional facts with currency units toward 'incomplete' in filingCoverage.
- **Verifier:** filing-statements.ts:80-84: fixed-zero is 'supported', but any text other than a dash goes through Number(), so 'no' becomes NaN, the value becomes null and a warning is added. numwordsen is unsupported. filingCoverage (:130) marks the filing incomplete, historical-record.ts:173 throws, and statement-repair.ts:50/:79-118 cannot relabel heading tables or clear warnings. I ran the extractor offline on the NuScale 10-K e8e16db7: a heading-identified balance table had 4 unresolved CommonStockSharesIssued facts, and status was 'incomplete'.

### RM3

**A model output that fails a deterministic post-check is replayed from the task cache on every resume, so the run cannot recover without a code change**  
Severity high · confirmed · effort M

Locations: `src/lib/research/run-context.ts:419-420`, `src/lib/research/handlers/company-genesis.ts:157-186`, `src/lib/research/artifacts/repository.ts:83-86`, `src/lib/research/handlers/operating-scenarios.ts:85-88`, `src/lib/research/handlers/historical-record.ts:172-174`, `src/lib/research/repair/agent.ts:25-33`, `src/lib/research/pipeline-runner.ts:35-37`

- **Evidence:** callResearchAgent reuses any completed task whose output passes the format schema (run-context.ts:419-420). Tasks are invalidated only by advanceStage validation failures (orchestrator.ts:313-314) or by being 'running' at startup (pipeline-runner.ts:35-37). A handler that throws after a successful call skips advanceStage, so its completed task stays reusable. Examples: company-genesis drops unknown citation IDs (157-163), which can empty a .min(1) evidence_claim_ids array, and upsertArtifact then throws 'Invalid company_genesis' (repository.ts:84-86). operating-scenarios throws at 85-88. historical-record throws when statement repair is unresolved (173), and the repair-module tasks are keyed by attempt number plus packet hash (repair/agent.ts:27), so the same failing modules are replayed. Observed: run 1d427f3f stopped at 21:15 with 'Decision synthesis cited evidence IDs outside the accepted packet'. The next job made a new call only because the code and prompt changed (PR #43).
- **Failure scenario:** Company genesis cites one mis-copied UUID as the only evidence for a founder motivation. The citation repair keeps it, dropInvalidCitationIds empties the array and upsertArtifact throws. Every re-enqueue reuses the same two cached outputs, hits the same throw and stops again. The run is stuck until someone edits code or deletes tasks by hand.
- **Fix:** When a stage handler rejects with a non-transient error, mark that stage's tasks completed during this attempt as invalid before failRun: UPDATE research_tasks SET validation_status='invalid' WHERE stage_id=… AND status='completed' AND completed_at >= stage.started_at. latestV3TaskOutput already skips invalid rows. Alternatively have callResearchAgent return the task id and invalidate it in the handler's catch. In company-genesis, also remove array entries whose citations become empty after dropping, rather than letting upsertArtifact throw.
- **Verifier:** completeV3Task runs inside callResearchAgent before the handler's post-checks. latestV3TaskOutput (run-context.ts:245-258) replays any completed, non-invalid task with the same request hash. Tasks are only invalidated at orchestrator.ts:313, team.ts:234 and run-context.ts:424 (schema change), and none of these runs when a handler throws. company-genesis.ts:157-186 drops IDs and then calls upsertArtifact, which throws on schema failure (repository.ts:84-86, with contracts.ts evidence_claim_ids .min(1)). So the same cached outputs reproduce the same throw on every resume, which wedges the run.

### G3

**SEC companyfacts and historical_diagnosis assume calendar quarters, so most non-December and 52/53-week filers lose their quarterly history**  
Severity medium · confirmed · effort M

Locations: `src/lib/research/history/sec-companyfacts.ts:64-74`, `src/lib/research/history/sec-companyfacts.ts:104-110`, `src/lib/research/history/sec-companyfacts.ts:118-123`, `src/lib/research/handlers/historical-diagnosis.ts:37`, `src/lib/research/handlers/historical-diagnosis.ts:40-45`, `src/lib/research/handlers/historical-record.ts:133-142`, `src/lib/research/handlers/historical-record.ts:178-186`, `src/lib/research/handlers/asset-valuation.ts:257`

- **Evidence:** quarterOf accepts a period only when its end is a calendar quarter-end date (:64-74), and secQuarterlyObservations drops every other row (:108). The YTD-to-quarter fallback only matches YTD facts that start on `${year}-01-01` (:119-122). historical-diagnosis reads only metric_observations (companyfacts plus model rows) and filters out any duration whose period_start is before date_trunc('quarter', period_end) (:37). It labels quarters by calendar month (:44-45), while historical_record labels its window with the filing's fiscal year and quarter (:178-179). historical-record also labels companyfacts and model rows by calendar quarter (:136-142) and merges them into the fiscal-labelled record wherever no filing observation has the same key (:181-186). Two clarifications: buildHistoricalDiagnosis never reads endFiscalYear/endFiscalQuarter (diagnosis.ts:23-110), so the window mismatch the brief raised has no effect; the labels are where the two artifacts disagree. And every asset run so far (META, SOFI, MELI) files on a calendar year; companyfacts gave META 20 quarters per metric.
- **Failure scenario:** Apple (quarter ending 2024-09-28), Intel and AMD (last Saturday of December), NVIDIA, Oracle and Nike (quarters ending Aug 31, Nov 30 and Feb 28): companyfacts yields no quarters, and the diagnosis filter also drops model quarters that start before the calendar quarter. historical_diagnosis therefore sees a handful of rows, and every metric comes out 'insufficient_history' at confidence 0.2. latestSecQuarterlyFact also returns null, so no diluted-share evidence claim is written. Microsoft (June fiscal year; an MSFT run is pending in the DB) loses Q4 revenue and net income and fiscal Q2-Q4 cash flows. Where its filings leave a gap, calendar-labelled 2024Q1 values (Jan-Mar 2024) fill the fiscal 2024Q1 slot (Jul-Sep 2023), and the diagnosis's '2024Q3' names a different period from the record's '2024Q3'.
- **Fix:** In sec-companyfacts.ts, identify quarters from the fact's own dates: a duration of 80-100 days, or SEC's `frame` field (CYyyyyQn, or CYyyyyQnI for instants). Derive a missing quarter as the YTD fact minus the prior YTD fact with the same `start`, not a 1 January start. In historical-diagnosis.ts:37, replace the date_trunc filter with a duration test (period_end - period_start between 80 and 100 days), and take fiscal labels from the run's financial_statement_set period map instead of the calendar.
- **Verifier:** sec-companyfacts.ts:64-74 quarterOf accepts only calendar quarter-end dates, :108 filters on it, and the YTD fallback at :119-122 requires a start of `${year}-01-01`, so 52/53-week, Aug/Nov/Feb and June-FY YTD/Q4 periods drop out. historical-diagnosis.ts:37 filters on date_trunc('quarter') and labels quarters by calendar month (:40-45), and it reads only metric_observations, which are written by corpus.ts:1917 and staging.ts:288, never from the filing statements. historical-record.ts:136-142 labels companyfacts and model rows by calendar month and merges them with fiscal-labelled filing rows. One detail is wrong: NVIDIA's quarters end in late Jan/Apr/Jul/Oct, not Aug/Nov/Feb, but those still fail quarterOf.

### G4

**asset_valuation throws whenever the diluted-share fact happens to straddle a 9,000-character chunk boundary**  
Severity medium · confirmed · effort S

Locations: `src/lib/research/handlers/asset-valuation.ts:252-279`, `src/lib/research/sources/corpus.ts:1505-1529`

- **Evidence:** After reading the full companyfacts file (:252), the handler looks for the diluted-share fact with LIKE matches on a single chunk: the val, start, end and accn strings must all be in that chunk. If no chunk has all four, it throws 'SEC diluted-share fact could not be linked to its source chunk' (:262-279).
